| DEV-1695 | 🐞 **BUG — `POST /consent/versions` lets any caller choose (and squat) a `consent_text_version` row's primary key.** `ConsentStore.CreateVersion` (`consent_impl.go:34`) clears `PublishedAt`/`PublishedBy`/`SupersededAt`/`CopiedMechanicsID` on a caller-supplied `TextVersion` before insert, but never clears `.ID` — and `routes/consent.go`'s `createVersionInput` decodes a caller-supplied `id` field straight into that struct. Demonstrated through the real `routes.ConsentRoutes` mux (sqlite, in-process): `POST /consent/versions {"id":"attacker-chosen-id","scope":"mechanics","version":"v1","language":"en"}` → `201 {"id":"attacker-chosen-id",...}` — the server stored the caller's literal string as the row's primary key, when every legitimate create mints `consentversion-<sequence-or-uuid>` via `gormstore.mintID`'s `BeforeCreate` hook (`gormstore/consent.go`), which only fires `if r.ID == ""`. On Postgres, ids are sequential (`consentversion-1`, `consentversion-2`, ...) — a caller who pre-creates a row at a future sequence number can make a later legitimate auto-minted create collide on that primary key and fail. Pinning test: `routes/consent_routes_test.go`'s `TestCreateConsentVersion_HonorsCallerSuppliedID` (real mux, sqlite; currently green, asserting the *broken* behavior — will fail once the fix lands, per the test's own comment). | 📋 Not Started | — |
