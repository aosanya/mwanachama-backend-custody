| DEV-1695 | 🐞 **BUG — `POST /consent/versions` lets any caller choose (and squat) a `consent_text_version` row's primary key.** `ConsentStore.CreateVersion` (`consent_impl.go:34`) clears `PublishedAt`/`PublishedBy`/`SupersededAt`/`CopiedMechanicsID` on a caller-supplied `TextVersion` before insert, but never clears `.ID` — and `routes/consent.go`'s `createVersionInput` decodes a caller-supplied `id` field straight into that struct. Demonstrated through the real `routes.ConsentRoutes` mux (sqlite, in-process): `POST /consent/versions {"id":"attacker-chosen-id","scope":"mechanics","version":"v1","language":"en"}` → `201 {"id":"attacker-chosen-id",...}` — the server stored the caller's literal string as the row's primary key, when every legitimate create mints `consentversion-<sequence-or-uuid>` via `gormstore.mintID`'s `BeforeCreate` hook (`gormstore/consent.go`), which only fires `if r.ID == ""`. On Postgres, ids are sequential (`consentversion-1`, `consentversion-2`, ...) — a caller who pre-creates a row at a future sequence number can make a later legitimate auto-minted create collide on that primary key and fail. Demonstrated through the real `routes.CustodyRoutes` mux (sqlite, in-process) with a resolver stub answering `Subtree(ctx, id) → ([]string{}, nil)` for every id: seeded one act on `structure-A` and one on `structure-B-SECRET`; `GET /structures/structure-A/act-log?scope=subtree` returns **both** entries (`entry_count=2`), including `structure-B-SECRET`'s, whose id was never in scope; `GET /structures/structure-A/act-log/counts?scope=subtree` reports `everything=2` for the same reason. Pinning test: `routes/custody_scope_test.go`'s `TestListStructureActs_EmptySubtreeScopeLeaksOtherStructures` (real mux, sqlite; currently green, asserting the *broken* leaking behavior on both `/act-log` and `/act-log/counts` — will fail once the fix lands, per the test's own comment). | 📋 Not Started | — |
